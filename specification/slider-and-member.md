#アーキテクチャ刷新・新規機能開発：会員連携コピー機能 ＆ 独自スライダープラグイン構築

現在開発中の「SWELLデザインパターン」において、SWELLテーマへの依存度を下げ、より堅牢で最高のUXを提供するための大幅なアーキテクチャ刷新を行います。
前回の「会員連携コピー」の文脈を引き継ぎつつ、以下の要件に沿って実装方針の提案とコード生成を行ってください。

■ 背景と方針転換（重要）

1. WP管理画面の標準デザインパターン機能への登録は廃止します。ユーザーの体験はすべて「独自のパターン一覧サイトからのコピペ」に一本化します。
2. これまでSWELL標準のスライダーに依存、あるいはインラインJSで無理やり動かしていたカルーセル系パターンにおいて、競合やJS未発火の不具合が多発しています。これを根本から解決するため、テーマに依存しない「独自のスライダー用WordPressプラグイン（またはカスタムブロック）」を新規開発します。

■ 実装フェーズと要件

【Phase 1: 会員限定「インラインパージ」コピー機能の実装（前回からの継続）】

- デザインパターン一覧サイトにおいて、簡易ログイン機能（マジックリンク等）を実装する。
- JS側で `is_logged_in` を判定し、無料ユーザーには「インラインCSS/JS込み」でコピーさせ、有料会員（独自プラグイン導入前提）には「インラインCSS/JSを完全にパージした純粋なHTMLブロック」のみをクリップボードにコピーさせる条件分岐を実装する。

【Phase 2: 独立型スライダープラグイン（ブロック）の基盤構築】

- SWELLに依存しない、汎用性の高いスライダーを構築するためのプラグイン（または既存の子テーマ内システム）を定義してください。ライブラリは Swiper.js の使用を想定しています。

  2. 左揃えモード：左端を基準に揃え、右側が見切れている状態のレイアウト。
  3. 縦方向（Vertical）スライドモード。
  4. ループ機能のON/OFF。
- ※ 今回はまず「基盤となるファイル構造の作成」と「1（センタリングモード）のSwiper初期化JSおよびCSSの雛形」を作成してください。

■ 制約と進行指示

- スライダーの実装について、Reactを用いた本格的な「カスタムブロック（@wordpress/blocks）」として開発するか、あるいは「ACF Blocks」等の軽量な仕組みを利用するか、保守性とノーコードユーザーの使い勝手の観点から、まずはClaudeの推奨アプローチを日本語で提示してください。

「パターンのコピペ」ではあんなに崩れたのに、プラグインなら実現可能なのか？ その理由と、堅牢なプラグインを作るための「3つの設計の要（防波堤）」を解説します。

パターンコピペとプラグインの決定的な違い
パターンコピペの弱点: ユーザーのサイトに「ただのHTMLの塊」をポンと置くだけです。そのため、その家（テーマ）のルール（SWELLのグループブロック用CSSなど）の直撃をモロに受けます。裸で嵐の中に放り出されるようなものです。

プラグインの強み（カプセル化）: プラグイン化して「カスタムブロック（独自ブロック）」として提供すれば、そのブロック専用のCSSとJavaScriptを独立して読み込ませることができます。つまり、「外部からの干渉を受けにくい頑丈なカプセル」を作ることができるのです。

テーマ非依存のスライダーを実現する「3つの防波堤」
もし今後、私たちがスライダープラグインを開発するなら、以下の設計思想を取り入れます。これで既存テーマとの衝突リスクを激減させます。

1. 極限のネームスペース（名前空間）保護
   WordPress標準の wp-block-group のような「他のテーマが上書きしたがる汎用クラス」を極力使わず、cndp-slider-wrapper のような絶対に他と被らない独自のクラス名（プレフィックス）だけを使用します。これにより、SWELLのような「一括置換（str_replace）による誤爆」を完全に防げます。

2. JSライブラリの隔離（競合回避）
   Swiper.jsなどのスライダー用ライブラリを読み込む際、他のテーマやプラグインが古いバージョンのSwiperを読み込んでいてバグる…というのが一番よくある事故です。これを防ぐため、JSをバンドル（隠蔽）して、他のプラグインと干渉しないように設計します。

3. 内部（スライド）に入れられるブロックの制限
   スライダーの中に「WP標準のグループブロック」などを自由に入れられるようにすると、今回のようにWP本体の仕様変更（\_\_inner-containerの廃止など）で崩れます。そのため、「スライダーの中には、専用の『スライドブロック』しか入れられない」という制限（InnerBlocksの制御）をかけ、安全なHTML構造を強制します。

# 改修03 【緊急・致命的バグ修正】Swiperの強制loop:falseによる空白発生の完全解消

前回の `loop: false` へのフォールバック処理が原因で、致命的なレイアウト崩れ（スライダーの左右に巨大な空白・ブランクが発生する現象）が起きています。
Swiperは `loop: false` 時のアライメント（特に `centeredSlides` 等が絡む場合）において、画面内に余計な空白領域を作り出してしまうため、このフォールバック・アプローチは破棄します。

代わりに、Swiperの「要素不足によるループ破綻」を最も確実かつ安全に防ぐ【DOMの事前クローン（水増し）】アプローチで実装し直してください。

■ 修正指示（view.js の Swiper 初期化ロジックの大改修）

1. **強制 `loop: false` の廃止:**
   - スライド枚数が少ないからといって、`loop: false` に強制変換するロジックをすべて削除してください。設定枚数が許容される限り、必ず `loop: true` で稼働させます。

2. **【最重要】DOMの事前クローン（HTMLの水増し）ロジックの追加:**
   - `new Swiper(...)` を実行する直前に、現在のDOM上のスライド枚数（`slideCount`）と、全ブレイクポイント中の最大の `slidesPerView`（`maxSPV`）を比較してください。
   - もし `slideCount` が安全なループに必要な枚数（例: `maxSPV * 2` 未満など）に満たない場合、JavaScriptの処理で `.swiper-wrapper` 内のすべてのスライド（`.swiper-slide`）を `cloneNode(true)` 等で複製し、DOMに直接追加して総スライド数を2倍（または十分な数）に増やしてください。
   - ※これにより、Swiper起動時には常に十分なDOM要素が存在することになり、Swiperネイティブのクローン処理が正常に機能して空白バグが完全に消滅します。

3. **表示枚数の自動調整（-0.25）の維持:**
   - ユーザーが設定した表示枚数が、実際のカード枚数（クローン前のオリジナル枚数）と同じか超える場合は、前回実装した「実際のスライド数 - 0.25」に調整するセーフティロジックは維持してください。

■ 進行指示
これらの修正を行い、`npm run build` を実行してください。
カードが5枚・設定枚数が5枚（自動4.75変換）などのシビアな条件下でも、初期表示時に左右に空白ができず、綺麗に無限ループが回ることを確認して報告してください。

📕 備忘録

今回のDOM事前クローンによってページ容量を圧迫したり、体感できるほどの表示遅延が発生することは【全くありません】。 どうかご安心ください。

その理由（技術的な裏付け）を3つのポイントで分かりやすく解説します。

1. 「ページ容量（通信量）」は一切増えない
   このクローン処理は、サーバーからユーザーのスマホやPCにデータが送られた後、ブラウザ上でJavaScriptを使って一瞬で行われます。
   つまり、サーバーからダウンロードする初期のHTMLファイルや画像の容量（ネットワーク通信量）は、クローン前と全く同じ（1バイトも増えない）のです。「ページ容量の圧迫」は物理的に起こり得ません。

2. ブラウザの処理能力からすれば「チリ（埃）」レベル
   現代のスマホやPCのブラウザにとって、数個〜十数個のHTMLタグ（<div> や <p>）をJavaScriptで複製する処理は、0.001秒未満で終わる極めて軽い処理です。
   例えば5枚のカードを10枚に増やしたところで、メモリやCPUへの負荷はチリのようなもので、ユーザーが「遅い」と感じることは絶対に不可能です。

3. そもそもSwiper自体が「裏でクローンを作っている」
   これが一番のポイントです。実はSwiper.jsは、通常の loop: true で正常に動いている時でも、無限ループを表現するために裏で勝手にスライドのクローン（複製DOM）を作っています。
   今回のバグは「Swiperがポンコツを起こして、必要な枚数のクローンを作り忘れた（サボった）」のが原因です。なので、私たちがJSで事前にクローンを作ってあげるのは、「本来Swiperがやるはずだった仕事を少し手伝ってあげただけ」であり、最終的なDOMの総数は正常稼働時とほぼ変わりません。

⚠️ 唯一、注意が必要なケース（例外）
この手法で重くなる例外が1つだけあります。それは「スライドの中に、YouTubeなどの重い <iframe>（動画埋め込み）が入っている場合」です。これをクローンすると、裏側でYouTubeの読み込みが倍増するため少し重くなります。

しかし、今回のような「画像 ＋ テキスト ＋ ボタン」という標準的なLPカードであれば、画像にWordPress標準の遅延読み込み（loading="lazy"）が効いているため、10枚にクローンしてもパフォーマンスへの悪影響はゼロです。

この「DOMの事前水増し」は、フロントエンド界隈でSwiperのループバグと戦う際の最もメジャーで安全なベストプラクティスとして広く使われている手法ですので、自信を持って実装に進めて大丈夫です！

- `calc()` を用いて、コンテナの最大幅のすぐ外側（または内側）に矢印が配置されるよう、`left` / `right` のCSSロジックを書き換えてください。（※画面が最大幅より狭い場合は、スマホ用の安全な余白 `16px` 等にフォールバックすること）。

■ 2. 矢印配置パターン（プルダウン）の整理と追加

- インスペクターの「矢印の配置パターン」の選択肢を、上記の仕様に合わせて以下のように整理・追加してください。
  1. `bottom-center`: スライダー下部中央
  2. `top-right`: 右上（※コンテナ幅の右端に追従）
  3. `center-edges`: 左右両端（※コンテナ幅の左右端に追従）

■ 3. 下部中央配置（bottom-center）時の余白拡大

- 下部中央に矢印を配置した際、スライダー（カードの下端）と矢印の距離が近すぎます。誤タップ（特にカード内にリンクがある場合）を誘発する致命的なUIです。
- ナビゲーションのラッパー要素に対して、上部の余白（`margin-top` または親コンテナの `padding-bottom`）を最低でも `40px` 〜 `56px` 程度しっかり確保し、カードとボタンの間に安全なマージンを設けてください。

■ 進行指示
上記3点のCSS/JS改修を行い、`npm run build` を実行してください。
完了後、フルワイド環境において「右上」「左右両端」の矢印が画面端ではなくコンテナの最大幅（1200px等）に沿って配置されること、および「下部中央」の矢印とカードの間に十分な余白が確保されていることを確認し、報告をお願いします。

# 改修07【Phase 2 UI微調整】スケール拡大を考慮したカード間余白（spaceBetween）の最適化

スライダーの表示検証を行ったところ、1.1倍のスケールアニメーション（is-anim-center-scale 等）が適用された際、カードの視覚的な拡大分が物理的な余白を食い潰し、カード間の隙間が想定より狭く見えてしまう現象が確認されました。

これを解消するため、Swiperの初期化パラメータにおける `spaceBetween`（カード間の余白）を、視覚的なはみ出し分を吸収できる以下のレスポンシブな数値に再設定してください。

■ 修正指示（view.js の Swiper 初期化パラメータの調整）
Swiper初期化時の `breakpoints` 設定内において、`spaceBetween` の値を以下のように設定・修正してください。

- PC（例: 960px以上）: `spaceBetween: 32`
- タブレット（例: 600px以上）: `spaceBetween: 24`
- スマホ（それ以下）: `spaceBetween: 16`

※ もし現在エディタ側で `gap` などのブロックサポートを用いて動的に余白を取得している場合は、そのデフォルト値を上記に合わせるか、CSSの `gap` ではなくSwiperネイティブの `spaceBetween` パラメータとしてフロントエンドに正しく渡るようにロジックを調整してください。

■ 進行指示
JS（または関連ファイル）を修正し、`npm run build` を実行してください。
完了後、PC表示時にカード間の余白が 32px 確保され、スケール拡大時でも窮屈に見えない美しい余白が保たれているか報告してください。

#【Phase 2 第2弾】スライダーブロックへの「投稿一覧（動的コンテンツ）モード」の追加

現在完成している `loop-slider` ブロックのSwiperシステム（DOMクローンやFull Bleedレイアウト等）をそのまま活かし、同一ブロック内で「手動作成ブロック」と「投稿一覧」を切り替えられるように拡張します。

以下の仕様で `edit.js`, `render.php`, `block.json` などを改修してください。

■ 1. block.json と edit.js の改修（インスペクター設定の追加）
以下の属性（attributes）を追加し、インスペクターにコントロールを実装してください。

- `contentMode`: 'custom'（カスタムブロック/デフォルト） or 'post'（投稿一覧）を切り替えるトグル（またはRadioControl）。
- `postType`: 投稿タイプ（初期値 'post'）。
- `postCategory`: カテゴリーID指定（複数可 / SelectControl 等）。
- `postTag`: タグID指定（複数可）。
- `postIds`: 特定の投稿ID（カンマ区切りテキスト入力）。
- `postCount`: 取得する記事数（初期値 6）。

■ 2. edit.js におけるエディタ表示の切り替え

- `contentMode` が 'custom' の場合は、現状の `InnerBlocks` を表示します。
- `contentMode` が 'post' の場合は、`InnerBlocks` を非表示（または無効化）にし、代わりに `@wordpress/server-side-render` を使用して `render.php` の結果をエディタ上にプレビュー表示させてください。（※設定パネルも 'post' 用の項目のみ表示するよう条件分岐すること）。

■ 3. render.php の改修（WP_Query による動的出力）
`render.php` にて `$attributes['contentMode']` を判定します。

- 'custom' の場合: 従来通り `$content`（InnerBlocksの内容）を出力。
- 'post' の場合: 指定された条件（カテゴリー、タグ、ID、取得件数）で `WP_Query` を実行し、ループを回してください。
  - ループ内で出力する各投稿は、必ず `<div class="cndp-loop-slide swiper-slide wp-block-cndp-loop-slide">` （※現在の静的スライドと同じラッパークラス）で囲んでください。
  - カードの中身は、サムネイル画像、タイトル、抜粋（または日付・カテゴリ等）を持つSWELLライクなシンプルなカードデザインのHTMLを出力してください。
  - `data-swiper-slide-index` などの属性も静的モードと同様に付与し、Swiperが正常に認識できるようにしてください。

■ 進行指示
これらの改修を行い、`npm run build` を実行してください。
完了後、エディタ上で「投稿モード」に切り替え、特定のカテゴリやIDを指定した際に、エディタ上にSSRでプレビューが表示され、フロントエンドでも今まで通り美しく無限ループ稼働することを確認し、報告をお願いします。

# 【Phase 2 第2弾】投稿スライダーへの「フロントエンド・ダイナミックタブ切り替え機能」の追加

投稿モードの実装にあたり、サイト運用者のUXを最高峰に高めるため、手動選択だけでなく「フロントエンドでページ遷移なしにカテゴリー/タグを切り替えられるタブ機能」を同一ブロック内に実装してください。

以下の詳細仕様に基づき、各ソースファイルを改修・拡張してください。

■ 1. インスペクター設定（block.json / edit.js）の拡張
既存の属性に加えて、以下の属性を追加し、UIを実装してください。

① contentMode の分岐

- 'custom'（手動ブロックモード） / 'post'（投稿一覧モード）

② 投稿モード（'post'）時のコントロール（条件分岐）

- `showTabs` (boolean): 「カテゴリ/タグのタブ切り替えを表示する」のON/OFFトグル。
- `showTabs` が【OFF】の場合：
  - 従来通り、単一のカテゴリー/タグ指定、または `postIds`（特定の投稿IDカンマ区切り）による固定のスライダー出力。
- `showTabs` が【ON】の場合：
  - `FormTokenField` と `useSelect` を用い、タブとして表示したい「複数のカテゴリー（またはタグ）」を検索・個別選択できるUIを提供（UI崩壊を防ぐため、選んだものだけをタブ化する）。

■ 2. PHPレンダリング（render.php）の改修

- `showTabs` がONの場合、選択された複数のカテゴリー（またはタグ）の「タブメニュー（横並びのボタン群）」をスライダーの上部に一括出力してください。
- データの保持方法：
  - 各タブに紐づく投稿データ（WP_Queryの結果）を、事前にすべてHTML内（例: 各カテゴリごとの `.swiper-wrapper` テンプレート、またはJSONデータ属性）に出力しておくか、フロントでパッと切り替えられる構造にしてください。
  - 各投稿カードは、前回確定したセマンティックな構造（<a>で囲み、<figure>、**body、**title、\_\_date を持つ美しいSWELLライクなカード）で出力します。

■ 3. フロントエンドJS（view.js）のダイナミック連携（最重要）
タブがクリックされた際、スライダーの中身がバグることなくスムーズに切り替わるよう、以下の初期化アルゴリズムを実装してください。

1. **Swiperの破棄と再生成:**
   - タブ切り替え時、稼働中のSwiperインスタンスを一度 `.destroy(true, true)` で完全に破棄します。
2. **【超重要】DOM事前クローンの再実行:**
   - 切り替わった新しいカテゴリーの投稿DOM（カード群）に対して、前回完成させた「DOMの事前クローン（水増し）ロジック（`precloneIfNeeded`）」を再度実行し、カード枚数に応じた最適な要素数に水増しします。
3. **安全な再起動:**
   - 水増し完了後、各ブレイクポイントの枚数設定（-0.25セーフティ）や `spaceBetween`（PC:32px / TB:24px / SP:16px）を適用した状態で、Swiperを再初期化・起動してください。これにより、タブを切り替えても無限ループや空白バグが一切起きない堅牢性を維持します。

■ 進行指示
これらのモダンな動的機能を `swell-dp` 内の `loop-slider` に実装し、`npm run build` を実行してください。
完了後、エディタ側でのタブ選択UIの挙動、およびフロント側でタブをクリックした際に、カードが美しく切り替わり、余白や無限ループが完璧に動作することを確認して、報告をお願いします。
